# 12. Конектори імпорту й довідники (адміністратор)

**Вимоги:** FR-17 (конектори), FR-43 (довідники) · **Прецеденти:** UC-20, UC-14 · **Правила:** DG-16 (походження),
DG-17 (зміни налаштувань — у журнал) · табл. 3.31 (пороги Q-06, Q-07).

**Код:** `backend/app/api/admin_config.py`, `backend/app/ingestion/schedule.py` (розклад),
`backend/app/ingestion/sources.py` → `parse_official_csv()` (резервний імпорт), `backend/app/ingestion/service.py` → `run_all()`;
міграція `0008` (коди країн); сторінки `frontend/src/pages/AdminConfigPages.tsx`.
**Тести:** `backend/tests/test_e6v.py` — `test_connectors_*`, `test_connector_csv_fallback`, `test_scheduled_run_only_when_due`,
`test_dictionaries`.

## Ідея одним реченням
Адміністратор керує **звідки й коли** приходять відкриті дані та **якими кодами** їх описано. Кожна зміна потрапляє в журнал
аудиту зі старим і новим значенням (постумова UC-20). Самі дані він змінити не може — лише запустити імпорт, який проходить
ті самі перевірки якості.

## Конектори (`/admin/connectors`, FR-17)
10 конекторів — по одному на відкритий показник (World Bank — 7, IMF — 2, BIS — 1).

| Дія | Запит | Що відбувається | Журнал |
|---|---|---|---|
| переглянути | `GET /api/admin/connectors` | розклад, стан, **наступний запуск**, 5 останніх запусків | — |
| журнал запусків | `GET …/{id}/runs` | час, як запущено (розклад / вручну), результат, записів, адреса запиту, **SHA-256 сирих даних** | — |
| змінити розклад | `PATCH …/{id}` `{schedule}` | вираз cron перевіряється; **неправильний — 422 `INVALID_SCHEDULE` з причиною, нічого не змінюється** (UC-20 EX1) | `CONFIG_CHANGE`: `schedule: [старе, нове]` |
| увімкнути / вимкнути | `PATCH …/{id}` `{is_enabled}` | вимкнений конектор не запускається ні за розкладом, ні загальним ручним запуском | `CONFIG_CHANGE` |
| запустити зараз | `POST …/{id}/run` | запуск у фоні (UC-20 AC1 → UC-14), 202; результат — у журналі запусків | `CONFIG_CHANGE` (`manual_run`) + `DATASET_PUBLISH` |
| резервний імпорт | `POST …/{id}/upload` (файл) | див. нижче (UC-20 AC4) | `CONFIG_CHANGE` + `DATASET_PUBLISH` |

### Розклад (S-37)
- Формат — **cron із 5 полів** «хвилина година день місяць день_тижня»: `0 3 * * 1` — щопонеділка (типово),
  `0 3 1 * *` — першого числа, `0 3 * * 1-5` — у будні. Підтримуються `*`, числа, списки, діапазони, кроки (`*/2`).
- Щодня після 03:00 UTC сервер запускає конектори, **чий розклад припадає на цей день** (`schedule.due_on`; див. «Службові
  задачі» нижче). Хвилину й годину лише перевіряємо — точний час визначає планувальник.
- Ручний запуск (`import.yml` → Run workflow, «Запустити» біля конектора, «Запустити зараз» у службових задачах) ігнорує розклад.

### Службові задачі й «наздоганяння» (S-40)
Розклад GitHub Actions виявився ненадійним (23.11 запуск о 03:00 UTC стартував близько 12:00, 25.11 — не стартував).
Тому **сервер запускає задачі дня сам** (`app/core/scheduler.py`):
- після **03:00 UTC** перший запит дня — відвідувач, будильник GitHub (`daily.yml` о 03:23, `POST /api/internal/jobs/daily`)
  чи адміністратор — запускає у фоні дві задачі:
  - **daily** — завершення дозволів і нагадування (UC-19, UC-09 EX2), строки зберігання (DG-23, DG-24), **резервна копія** (NFR-10);
  - **import** — конектори, чий розклад припадає на сьогодні;
- умовний `UPDATE` у таблиці `job_runs` гарантує **один запуск на день**, хоч би скільки викликів прийшло;
- Render Free засинає без відвідувачів — тоді задачі виконаються з першим запитом наступного дня (вони ідемпотентні,
  а строк дозволу й так перевіряється на кожному запиті, DG-05).

На сторінці «Конектори» розділ **«Службові задачі»** (`GET /api/admin/jobs`): коли востаннє, хто запустив (будильник GitHub /
сервер сам / адміністратор), результат (скільки дозволів завершено, нагадувань, анонімізацій, назва резервної копії).
**«Запустити зараз»** (`POST /api/admin/jobs/{daily|import}/run`) — негайно, навіть якщо сьогодні вже запускалось;
`import` вручну запускає **всі** увімкнені конектори. Журнал — `CONFIG_CHANGE` (`manual_run`).

### Резервні копії (NFR-10, S-40)
Частина задачі `daily` (`app/core/backup.py`): через Neon API створюється гілка-знімок `backup-РРРР-ММ-ДД` (миттєва,
copy-on-write, у тому самому регіоні ЄС), зберігаються **7 останніх**, старші видаляються. Ключ і ID проєкту — лише
в змінних середовища Render `NEON_API_KEY`, `NEON_PROJECT_ID`; без них копія пропускається (видно в «Службових задачах»).
**Відновлення:** Neon → Branches → основна гілка → Restore з потрібного знімка (або тимчасово перемкнути `DATABASE_URL`
на гілку-знімок) — хвилини, що вкладається в NFR-10 (≤ 4 год).

### Резервний імпорт з CSV (UC-20 AC4)
Якщо API джерела тривалий час недоступний, адміністратор завантажує **офіційний CSV-експорт** джерела:
1. **World Bank — файл як є** (`API_<ряд>_DS2_…csv` з сайту data.worldbank.org): службові рядки зверху пропускаються,
   береться рядок саме того ряду, що й у конектора (інший ряд — 422 `UNSUPPORTED_CSV` «це експорт іншого показника»);
2. **IMF і BIS** — їхні експорти, збережені як CSV з колонками `country,year,value` (ISO3, рік, значення в одиницях джерела).

Далі — **ті самі кроки UC-14**: лише країни платформи й роки від 2000, та сама гармонізація (масштаб), перевірки якості
Q-02 – Q-10, нова версія лише за зміни значень. Файл зберігається як сира відповідь із SHA-256 (90 днів), а в журналі
запусків адреса запиту має вигляд `file:<назва файлу>` — тож походження версії (файл 9) показує, що дані прийшли з файлу.
До 5 МБ.

## Довідники (`/admin/reference`, FR-43)
| Довідник | Що можна | Обмеження |
|---|---|---|
| **Країни** (UC-20 AC2) | додати: ISO3, назви UA / EN, **alpha-2** (для BIS) і **числовий код** (для контуру на карті); змінити; деактивувати | неактивна країна не імпортується, її наявні дані лишаються (D-05). Нова країна стає **зеленою на карті після наступного імпорту** |
| **Показники** (UC-20 AC3) | додати: код, назви, визначення, одиниця, масштаб, частота, **діапазони Q-06 і Q-07**; змінити; деактивувати | типовий діапазон має лежати в межах можливого (422 `INVALID_RANGES`); **показник із даними чи конектором не видаляється — лише деактивується** (409 `INDICATOR_HAS_DATA`, UC-20 EX2); частоту показника з даними не змінити |
| **Категорії закритих даних** | додати; змінити назви | — |
| **Організації** | створити верифіковану, верифікувати | на сторінці «Заявки на реєстрацію» (файл 4) |

Новий показник одразу доступний постачальникам у шаблоні завантаження (файл 3). Для відкритого показника потрібен ще й
конектор — це зміна коду (`sources.SPECS`), бо кожне джерело має свій формат.

Кожна зміна — `CONFIG_CHANGE` з `changes: {поле: [старе, нове]}`; створення й видалення — повний знімок запису.
Персональних даних у цих записах немає.

## Коди помилок
| Код | Коли |
|---|---|
| 403 `FORBIDDEN_ROLE` | не адміністратор |
| 422 `INVALID_SCHEDULE` | неправильний cron (з причиною) |
| 422 `UNSUPPORTED_CSV` | файл не схожий на експорт джерела або в ньому немає значень для країн платформи |
| 413 `FILE_TOO_LARGE` | файл понад 5 МБ |
| 409 `ALREADY_EXISTS` | код уже є |
| 409 `INDICATOR_HAS_DATA` | видалення показника з даними (EX2) або зміна його частоти |
| 422 `INVALID_RANGES`, `NOTHING_TO_UPDATE` | діапазони суперечать; нічого не змінено |
